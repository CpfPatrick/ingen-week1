# Week 2 reflection

The schema decision I am most likely to revisit is representing telemetry pose as local-map x and y coordinates plus heading without carrying a map identifier. That is a useful boundary for a small ingestion gateway: positions have explicit metre units, heading is counter-clockwise-positive radians, and the request does not pretend that latitude and longitude are interchangeable with a local map. However, a robot can change maps, restart its localization session, or be compared with another robot. The same numeric coordinates would then describe different places while still satisfying every Avro type check.

I have kept that limitation visible in the contract instead of inventing a map value. Required measurements have no zero defaults. The gateway checks finite numbers and ranges, while the documentation assigns responsibility for a consistent map origin to the client deployment. A future revision can add nullable, defaulted map and localization-session identifiers, then introduce an explicit transform before cross-map analytics. That extension needs semantic review as well as a schema-compatibility result; a readable event can still be misunderstood.

The second decision is separating submission identity from object identity. A frame is identified by robot, capture time normalized to milliseconds, and the SHA-256 of its exact bytes. Identical content can share a MinIO object across several capture events. PostgreSQL keeps the original event identity and first acceptance time, allowing an ordinary retry to return the same result. This avoids conflating a repeated request with a later observation of an unchanged scene. It also means future object deletion must consider all referring events rather than one row's age.

I have documented the remaining failure boundary explicitly. Kafka producer idempotence handles producer retries, but it does not atomically commit PostgreSQL, MinIO and Kafka together. A crash between broker acknowledgement and journal commit can redeliver the same event ID. Consumers therefore need event-ID deduplication; the implementation does not promise global exactly-once delivery. Telemetry retries have a different contract and receive new event IDs.

For evolution, I chose BACKWARD compatibility and an additive optional-camera example. New readers consuming old events demonstrate backward compatibility; old readers ignoring the new camera field demonstrate the opposite direction for that particular change. I will keep those statements separate when interpreting the test evidence. The contract, failure cases, curl examples and test commands describe what should be verified. Coverage, container-test outcomes and any deliberately failing CI branch must come from recorded runs, not from this reflection. The next stage should resolve map identity, downstream deduplication and privacy handling before processing real personal data.
